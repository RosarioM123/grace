Why I started this

I started TheGirlSavedByGrace in January 2020. I was 14. It came out of a rough stretch of my own: depression, anxiety, a lot of loneliness, and the way my Christian faith got me through it. I wrote for other teenagers who were in that same place and did not have anyone saying anything honest to them. That has not changed.

Since 2020 it has reached over 200,000 teenagers across 100 countries. I have used that figure in my PIMCO and BMO applications and it is the figure in the Grace business plan, so I am keeping it consistent here. The business plan also cites the wider numbers: 47 percent of Gen Z report mental health challenges, and youth suicide rose 62 percent between 2007 and 2021.

The audience is there. What is missing is any way to respond to one teenager, at the moment they write something, instead of publishing the same page for everyone.

What Grace is today

Today Grace is a static HTML site at rosariom123.github.io/grace. It holds the writing, the testimonies, and the community. There is no backend behind it. No login, no database, no code that reads what a visitor types.

The AI is planned. It is not built. It lives in the business plan. The live site has no AI in it. The $100,000 is what would build it, in the order described below. The only working piece is a small browser prototype I wrote to test the reading logic, and this page shows its actual code and its actual outputs so the mechanism is not a claim.

How it would work

A teenager opens Grace and writes how they are feeling, in their own words, in a free text box. There is no form with dropdowns and no score they can see themselves performing for. The writing is the input. A crisis check runs on that text before anything else is shown. If it flags, it overrides whatever response was going to appear and points the teenager to staffed help straight away: call or text 988, or text HOME to 741741. If there is no flag, the sentiment read decides the next screen: a testimony or video that fits what they wrote, a verse or prayer, or a concrete coping step. Where a teenager needs more than content, the system would match them to a licensed mental health professional. The target I am working to is plain: a teenager in crisis reaches a licensed professional the same day.

Stack from the business plan: ReactJS on the front end, MySQL for the database, hosted on AWS EC2, with spaCy and NLTK for the language work.

The word list

The prototype does not use a model. It uses a word list I wrote by hand: 24 words, each with a weight between -1 and +1. The score for a message is the average of the weights of the words it contains. Part of the list, exactly as written:

hopeless -0.9   alone -0.8   numb -0.7   lonely -0.7   panic -0.7
anxious -0.6   overwhelmed -0.6   sad -0.5   crying -0.5   tired -0.3
grateful +0.8   thankful +0.8   hopeful +0.7   loved +0.7   calm +0.5

The trade-off is stated plainly: a hand-written list runs in the browser with no server and anyone can read exactly why a message scored the way it did, and I gave up accuracy to get that. Teenagers write in slang, misspellings, and sentences where one word reverses another. A 24-word list misses most of that, which is why the production system uses spaCy and NLTK instead. The list exists to test the routing logic, not to ship.

The lookup itself, shortened only by showing 5 of the 24 entries:

const LEXICON = { hopeless: -0.9, alone: -0.8, numb: -0.7,
                  tired: -0.3, grateful: 0.8 }; // 5 of 24 entries
const CRISIS = ["hurt myself", "hurting myself",
                "want to die", "end it all"];

function readMessage(text) {
  const lower = text.toLowerCase();
  const words = lower.split(/[^a-z']+/);
  const hits = words.filter(w => w in LEXICON);
  const score = hits.length
    ? hits.reduce((s, w) => s + LEXICON[w], 0) / hits.length
    : 0;
  const crisis = CRISIS.some(p => lower.includes(p));
  return { score, hits, crisis };
  // crisis is returned separately and checked before
  // the score is allowed to route anything
}

What the prototype does on real phrases

These are the five test phrases I run against the prototype, written the way teenagers actually type, and the outputs the code above produces on them. Nothing here is rounded into a nicer story.

What they typedScoreRouteWords matched
idk i just feel numb -0.70 Content: testimony and a coping step numb -0.7
cant sleep again my chest feels tight im so anxious -0.60 Content: verse or prayer, breathing step anxious -0.6
i dont want to be here anymore i keep thinking about hurting myself 0.00 Crisis protocol, overrides the score phrase: "hurting myself"
feeling grateful today, church was good and i actually feel hopeful +0.75 Content: testimony to share, community prompt grateful +0.8, hopeful +0.7
im fine i guess, just tired and whatever -0.10 Unsure. See below. fine +0.1, tired -0.3

Two things in that table are worth noticing. The crisis phrase scores 0.00 on sentiment because none of its words are in the list, and it still routes to the crisis protocol, because the crisis check does not depend on the score. And the last phrase is a case the system cannot read: "fine" and "tired" nearly cancel out, and the honest answer is that the words do not say enough. In that case the page says it is not sure, in plain words rather than as an error, shows the crisis resources anyway, and flags the message for a human to review. A system that always sounds certain about a teenager's feelings would be lying some of the time. I would rather it admit the gap.

The safety layer

My decision: two separate checks instead of one. One check reads the teenager's message as it comes in, against a written safety policy that names what counts as risk language. A second check reads the response before it is shown, against the same policy. A flag from either one overrides the personalized response. Before any version ships, I run a set of crisis messages I wrote to try to break it, phrased the ways teenagers actually phrase them, including the ones that do not use obvious words. The version only ships if it catches them.

What I gave up: a second check costs time on every message and doubles the surface that can produce a false alarm. I accepted that because the failure in the other direction is worse. If the input check misses a crisis message, the output check is a second chance to catch it, and the resources are printed on every page of the site regardless, so a miss does not leave a teenager with nothing. If the check flags a message that was not a crisis, the cost is that a teenager sees helpline numbers they did not need, which is annoying and not dangerous.

Releases get scored before they go live on five things: sentiment accuracy, crisis recall (how many real crisis messages the system catches), crisis false-positive rate, response safety, and latency. Each one gets its threshold set in advance, with the clinicians reviewing the system, and if any one of them is crossed, that version does not ship until it is fixed. I am not publishing threshold numbers here because they get set with those clinicians, not guessed in advance by me.

How matching works

Matching a teenager to a professional is two lists compared, not one search. One side holds the teenager's signals: what they are feeling, the language they wrote in, faith preference, availability, and how urgent it is. The other side holds the professional's: specialty, language, faith background, availability, and verified credentials. Each side is turned into a vector, the match score starts from how close the two vectors are, and then a trust term is added on top, weighted by verified credentials and how recent the professional's activity is. Safety is not a filter applied after the ranking. It is inside the ranking, because a close match to an unverified person is not a good match.

The trade-off: a scored match is harder to explain than a simple rule like "first available." When a teenager asks why they got this person, I owe them an answer, so the system has to be able to show the two or three signals that drove the match in plain words. And if the match is wrong, because sometimes it will be, the teenager can ask for a different professional with one tap, without explaining themselves again.

The log

Every interaction is written once to a log that only ever gets appended to, never edited. Every action carries an idempotency key, a unique string generated when the action is first attempted, so if a phone retries a request on a bad connection, the retry is recognized and the teenager is not matched twice or sent the same message twice. One entry, in the format I use:

{ "id": "evt_1042", "key": "9f2c-req-771", "prev": "a41b", "hash": "sha256:7d3e...", "route": "crisis", "score": 0.00 }

Each entry stores the hash of the entry before it, so the chain breaks visibly if anything is altered later. This is a pattern I have already built for myself. WORLD, a deterministic state engine I wrote, keeps a SHA-256 hash-chained intent ledger and validates every state transition against capacity, liquidity, and node-lock constraints before it commits. The Grace log reuses that design: hash-chained entries, validation before commit, no silent overwrites. What I gave up is storage and simplicity. An append-only log grows forever and makes deleting a record a deliberate, visible act instead of a quiet one. For records about teenagers in crisis, I think that is the right side to err on.

What I would build first, in order

  1. The sentiment read, because everything downstream needs a feeling to work from. Matching has nothing to match on without it.
  2. The crisis check and the responses that go with it, because it has to be live and tested before any teenager sees a generated response. This is also where most of the risk sits, so it gets built while there is still time to fix it.
  3. Matching to licensed professionals, because it depends on the first two working: it routes by feeling, and a crisis match follows different rules from a content match.
  4. Scale last: a bigger content library, a wider professional network, and measuring whether any of it helps. I have not put dollar amounts against each step here because the plan I have does not split the $100,000 that way, and I would rather leave it unsplit than invent a breakdown.

On personalization specifically: a new way of matching content to a feeling ships to a small group first, gets measured against the current version on engagement and on whether teenagers actually reach a professional, and only rolls out to everyone if the numbers justify it. If an experiment cannot show a difference, the current version stays.

What could go wrong

Missing a crisis message. This is the risk that matters most. Teenagers do not always use the words a policy expects. The mitigations are the ones above: two checks instead of one, a red-team set written in real phrasing, crisis resources printed on every page so a miss is contained, and the unsure state routing to a human instead of guessing.

Matching to the wrong professional. A bad match at a bad moment can close a teenager off from asking again. The trust term keeps unverified professionals out of the top of the ranking, and the one-tap request for someone different means a wrong match is recoverable in seconds, not a dead end.

Teenagers not trusting a system with their feelings. This one is not fully solvable with engineering. What I can do: no account required to write something, the score is never shown to the teenager as a grade on how they feel, and the page is honest that a person, not the system, is the point of the matching step. If the sentiment read is wrong, the teenager sees content for the wrong feeling, so every response page also shows a simple way to pick a different feeling manually. The read is a suggestion, never a lock.

Open questions

Three things I have not decided, and I am not going to pretend otherwise in a funding document. First, whether matching should weight faith background above or below specialty. Grace is a faith-based community, so faith matters to the teenagers using it, but a closer specialty match may matter more in a crisis. I will test both orderings and let the outcomes decide. Second, whether the crisis check should run on the whole conversation or only the latest message. The whole conversation catches slow build-ups; the latest message is faster and easier to reason about. Third, how long interaction logs should be kept. The append-only design argues for keeping them; the fact that they are teenagers' words argues for a short retention window with a clear deletion date. That decision needs a clinician and a lawyer in the room, not just me.

How I built this

I wrote the prototype described on this page in an evening, to check whether the routing logic held up before writing about it in the application. The word list is hand-written, all 24 words, and so are the five test phrases, which are modeled on how teenagers in the Grace community actually write, with anything identifying removed. The scoring and the crisis check are the code shown above, running in the browser with no server call.
